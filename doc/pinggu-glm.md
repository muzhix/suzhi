## 一、总体评价

**结论：有条件通过。设计成熟度显著高于常见同类规划，可以启动阶段 A；但存在三个 P0 级缺口（核心价值假设缺少路线图门禁、EDU 采用漏斗未定义、实体链接验证过晚），建议补齐后再冻结 1.7 基线。**

这份规划最突出的特质不是"想得全"，而是**"删得狠 + 可证伪"**：用一张表显式取消九个中间领域对象（§5.2），把图检索、PPR、事件聚类全部置于"评测证明后才启用"的实验地位（D11、§23-C、§24.7、§25），并拒绝在无实验依据时预设质量阈值（§22.6）。多数知识图谱/文献平台项目的死亡路径——对象层级膨胀、图谱复杂度复发、图检索收益未经证明就固化为架构——在这份文档里都被预先封堵了。

主要不确定性不在设计质量，而集中在三处：**两个尚未验证的核心假设（EDU 抽取质量、实体链接质量）在路线图中的验证顺序和门禁设置有缺口**；**"候选→采用"的运营层设计是空白**；以及若干古籍场景特有的工程细节（中文全文检索、简繁异体归一）未落地。

## 二、方案的突出优势

1. **领域模型的克制是全局性优点。** §5.2 把证据、锚点、指称、命题、解释、解析、关系、事件框架、发现九个概念全部降级为 EDU 的组成部分或投影，并给出提升为独立对象的触发条件（独立查询/权限/版本/评审需求）。这直接规避了上一代知识工程"为概念对称性建对象"的复杂度陷阱。

2. **EDU 的粒度哲学有可操作判据。** §7.1 把 EDU 定位在三元组与长分块之间，§7.4 给出拆分/不拆分的具体规则，§13.3 的"不允许的推断"清单（谋害≠已杀害、"等"≠完整名单、"天下大悦"≠统计事实）把最容易跑偏的改写行为变成可核查的反例库。这是少见的把"忠实性"写成工程约束的尝试。

3. **补全来源三分法直击幻觉问题。** §8.3 的 Explicit/Contextual/External 分类，配合不变量 7（外部知识不得伪装成上下文补全）和 §22.1 金标准必须覆盖"只给当前段落"与"给正确上下文"两种输入，构成了对"模型记忆冒充文献依据"的完整防线。这是全方案学术可信度的基石，设计得很好。

4. **模型职责与系统职责的切分准确。** §12.1/§12.5 让模型只回显 `contextKey`、不生成 ID/哈希/偏移，把幻觉高发区（自造标识、自报依据、局部 ID 交叉引用）从输出契约中排除；§12.3 分层上下文包的标签与预算方案可直接实现。对 Spring Data JDBC 聚合保存语义（删除重建不适合不可变明细）的提前规避（§17.2）说明选型经过了真实推敲。

5. **图检索被当作可证伪的实验而非信仰。** D11 固定跳为默认、局部 PPR 为实验；§14.5 两种策略共用接口和输入输出；§23 阶段 C 设计了三组消融；§24.7 定义了 PPR 不显著优于固定跳时的处置；§25 把专用图数据库的引入条件写死为"实测延迟不达标"。PPR 的职责边界（只做图相关性排序，不理解"后来""因果"）表述精确。

6. **版本不可变与引用回溯的信任链完整。** D02/D03/D12 加 §18.3 九条不变量，从"OCR 重做不静默改变研究依据"到"删除原文不留悬空公开引用"，学术工具最关键的信任性质被系统化地覆盖，且多数不变量可直接翻译为集成测试。

7. **工程底座选择务实且论证到位。** PG 任务表 + `FOR UPDATE SKIP LOCKED`、S3 预签名直传 + 事后强校验 + 临时区、解析器接口隔离 MinerU（含境外连通性风险与上传模式取舍）、排除 Quartz/消息中间件/微服务的理由均成立。§17.6 对"Multipart ETag 不能当内容哈希""预签名 URL 视同临时凭据"这类细节的处理，达到了安全评审水准。

## 三、核心风险与缺口（按优先级）

### P0-1 核心价值假设缺少路线图门禁

§1.3 列出五项产品价值主张（比普通分块更易检索、比三元组保留更多语义……），但 §23 的阶段通过条件只覆盖"EDU 明显优于原有三元组或复杂对象输出"（阶段 A），**从头到尾没有把"EDU + 实体图检索优于同语料的朴素分块 RAG"设为任何阶段的门禁**。阶段 B、D 均无退出标准。

- **为什么重要**：整条批量抽取管线的成立逻辑是"一次抽取、多次查询摊销"。如果端到端对照显示朴素分块 RAG 在同一问答金标准上回答质量相当，那么批量 EDU 的成本结构不成立，平台退化为"带实体页的 RAG"——后者不需要 D04–D11 的绝大部分设计。
- **方案现有控制**：§22.3 有完整检索指标（EDU Recall@K、图扩展净新增等），但指标存在不等于被用作门禁。
- **建议**：在阶段 B 退出条件中加入同题库对照实验——EDU 通道 vs 原文分块 RAG 基线的 Recall@K、回答正确率、引用定位成功率、单问 token 成本；阶段 D 端到端复测一次。通过标准应表述为"EDU 通道不劣于基线，且提供基线无法提供的实体页/时间线/跨文献关联能力"，避免单一指标误杀。

### P0-2 "候选→采用"漏斗未定义，审核负担可能压垮工作流

§7.7 状态机有"候选（Proposed）/采用（Active）"，且 Active 才进入默认检索与图投影，但**全文没有定义批量采用的默认策略**：程序校验通过的候选 EDU 是默认进入检索，还是等待人工采用？

- 若等人工：一部中型古籍可产出数万条 EDU，逐条采用的点击量不可操作，§16.7 的批量审核队列再怎么排优先级也消化不了。
- 若默认采用：与全文反复强调的审核立场（§12.6 人工抽查、§22.1 金标准）形成张力，且 §16.7 的高影响队列成为唯一防线。
- **§24 风险清单中也没有"人工审核吞吐"这一项**——这是运营层的最大空白。
- **建议**：定义分层默认策略。程序校验通过且命中低风险信号（无外部知识补全、时间解析成功、quote 精确定位、无角色/实体类型冲突、非高影响范围）→ 自动采用并标注可信级别；命中 §16.7 任一高影响特征 → 进候选池等待；提供项目级开关"全部人工采用"。同时在 §24 增加 24.10"人工审核吞吐不足"及对应控制（自动采用 + 抽检率 + 高风险定向）。

### P0-3 实体链接是第二大技术假设，但验证被排到阶段 C 且无质量门

实体关联图的全部价值（D08）以及实体页、时间线、合并拆分（阶段 C 全部交付物）都依赖链接质量，而 §9.3 的五步链接管线恰是全方案中难度最高的 NLP 环节——古籍场景下字/号/谥号/庙号/官职性称谓的归一、同名消歧（唐代两个"王维"级别的问题）是领域级难题。

- 阶段 A 只验证 EDU 抽取，实体链接到阶段 C 才首次真实运行；§23-C 的通过条件里没有链接正确率指标（§22.2 有"实体链接正确率"，但未设门）。若链接质量不达标，阶段 C 的实体页和时间线将充满错误关联，且 §24.5 的"错误合并污染"会被放大。
- 冷启动也未处理：首个文档入库时项目实体表为空，所有提及都走"未链接文本值"，图的连通度在前期接近零。§4.2 的项目人物表是唯一种子来源，但如何从首批文档自举实体表没有描述。
- **建议**：把实体链接的最小可行性实验并入阶段 A（同一批金标准上加注期望实体与别名），或在阶段 B 末增加链接质量抽检门；为冷启动显式定义种子策略（项目人物表 + 传主 + 首文档高频实体候选表）；阶段 C 增加退出标准（实体链接正确率在两个领域金标准上达到阈值区间，阈值确定方式同 §22.6）。

### P1-4 成本与规模缺少量级估算

方案有完善的成本**指标**（§12.7、§20.1、§24.9），但全文没有任何量级**估算**：一部中型古籍（如《旧唐书》一传，约数万字到数十万字）产出多少 EDU、每条成本多少、全书处理时长、pgvector 在百万级 EDU 下的表现、审核工时。建议阶段 A 交付物明确包含"每千字处理成本曲线 + 全书处理预算表"，让 D14 的单库起点决策有数据支撑。

### P1-5 重复 EDU 与去重语义未定义

§12.2 说系统负责"去重"，但去重规则缺失。三个来源都会产生语义重复：重叠处理范围（§24.1 的控制手段本身制造重叠）、按需 EDU 生成（§14.3）、重跑（§20.2）。§19.4 的幂等键只防"完全相同的输入范围与配置"，防不了重叠窗口和按需场景。**建议**：定义 EDU 等价类规则（同文献版本 + 归一化谓词 + 等价参数集 + 相容时间 + 来源范围重叠度阈值），命中等价类时执行合并或 `supersedes`，并计入 §12.7 的重复率指标口径。

### P1-6 中文（尤古籍）全文检索与文本归一层缺失

§17.2 选用 PostgreSQL 全文检索，但 PG 默认分词配置对中文无效（无空格分隔，整句成单 token）；`pg_trgm` 只覆盖模糊名称匹配，不构成召回导向的全文方案。**需在 zhparser / pg_jieba / pg_bigm（或 trigram 相似度兜底）中做出选型并写入技术栈表。** 此外，简繁与异体字归一（郞→郎、勣保留不简化等，参见仓库内 dutongjian 字体排版分析所载词典策略）是古籍实体别名匹配与全文召回的硬需求，blueprint 完全未提及。建议在 §17.2 增加"检索归一层（NFKC + 简繁/异体映射 + 分词方案）"，并在 §9.3 链接第一步"精确匹配"之前强制名称规范化。

### P1-7 按需 EDU 生成的三个未决问题

§14.3/§19.3 的按需生成是"原文始终可检索"的关键机制，但存在三个未决点：

1. **延迟**：回答流程是否等待按需抽取完成？等待则问答延迟以十秒计，不等待则该轮回答用不上。建议明确为异步补全 + 本轮降级用原文回答，并在 §16.6 的"检索范围与截断提示"中标注。
2. **问题污染**：若"当前问题"参与补全上下文，生成的 EDU 带查询偏置，与金标准的可复现性冲突，作用域归属（§5.3）也不清。建议按需生成限定为"文献上下文-only"，问题只用于选择范围，不进入补全上下文；如此生成的 EDU 属文献级、可复用。
3. **重复**：与 P1-5 合并处理。

### P1-8 quote 校验对 OCR 语料脆弱

§12.6 要求原文摘录"确实出现在指定文本单元"（精确匹配）。OCR 文本本身有错字时，模型极易"顺手纠正"摘录导致校验失败，OCR 越差的语料拒绝率越高——恰是本平台最目标的人群。建议校验改用规范化 + 模糊匹配（trigram 相似度阈值），匹配差异在补全说明中区分"OCR 差异"与"模型改写"，前者放行、后者拒绝。

### P1-9 谓词开放词表的检索碎片化

谓词保持开放（§12.4.1）是正确取舍，但同一关系在不同运行/模型下会产出"谋害/暗害/加害"等变体，而 §14.1 把谓词列为检索对象，开放词表将打散谓词通道的召回。建议：提示词内提供"常用谓词建议表 + 允许自由值"，入库时做谓词归一/聚类映射，并与 §10.5 宽关系投影（`opposedTo` 等）共用同一张映射表，避免两套归一逻辑。

### P2-10 文献版本迁移旅程缺失

OCR 修复 → 新版本 → 项目重新绑定的完整用户旅程没有规划：EDU 重建的整份成本、能否按 diff 局部迁移、新旧版本引用对照 UI。D02 保证了不静默漂移，但"想换版本"是真实且高频的需求，目前唯一路径是全量重处理。

### P2-11 回答流式输出与任务轮询的边界需澄清

§17.8 "首期不使用 SSE"针对任务进度是成立的（数据库任务是进度权威）。但问答回答生成的 token 流式是聊天 UX 的基本预期，文档未单独决策。建议明确写成："任务进度走轮询；回答与文章生成走流式（SSE 或 chunked transfer）"，避免实施时把两者混用同一结论。

### P2-12 EDU 参数引用其他 EDU 的悬挂处理

§10.6 允许关系型 EDU 的参数引用其他 EDU（如 U8 引用 U5），但被引用方进入 `superseded` 或 `rejected` 时，引用方的处置未定义。不变量 4 只覆盖实体引用与文本值。建议补一条：被引用 EDU 替代时，引用方自动标记"需要复核"（复用 §4.6 既有机制）。

### P2-13 多通道分数融合方法未指定

§14.2 第 3 步"合并各通道分数"——向量分、全文分、图分不可直接比较。v1 用 RRF（倒数排名融合）即可，但应写明，否则实施时容易临时发明加权方案且不可复现。

### P2-14 其他小项

- 并发编辑：两人同时编辑同一 EDU、实体合并与编辑冲突，需乐观锁版本号。
- 实体作用域：§18.1 entity "项目或文献作用域"与 §9.3 "链接到项目已有实体"、§5.3 文献级复用之间的关系需一段明确。建议 v1 实体仅项目作用域，文献级只复用 EDU 不复用实体，链接成本按项目重复支付（显式接受该代价）。
- 图快捷边：视图 vs 物化视图的刷新时机（EDU 状态变化时）未定。
- 研究成果导出（docx/Markdown）未提及，对写作平台是显性缺口。
- 多租户数据隔离策略未提及（组织/项目两级是否共表）。
- Spring Boot 4.x + Spring AI 2.0 处于支持体系早期，预期少量适配成本；Java 21 稳妥，可备注 Java 25 LTS 为可选升级。
- 各阶段无工期与人力量级（A/B 约一人可跑，C/D 需前后端并进），作为规划文档属可接受的省略，但建议补一行量级。

## 四、技术栈评估

| 选型 | 评价 | 备注/建议 |
|---|---|---|
| Java 21 + Spring Boot 4.x | 认可 | 固定受支持小版本的写法正确；Boot 4 生态早期有适配成本，属可控 |
| Spring AI 2.0 | 认可 | 结构化输出 + 模型网关隔离（不向领域层暴露 Spring AI 类型）设计好；启动时校验模型 JSON Schema 能力、不静默降级，这条要保留 |
| Spring Data JDBC + JdbcClient | 认可 | 对聚合保存语义的规避准确；EDU 参数批量写入走显式 SQL 正确 |

| S3 预签名直传 | 认可 | 校验、临时区、生命周期清理、URL 当凭据的处理完整，达安全评审水准 |

## 五、内部一致性检查

**总体结论：高度自洽。** D01–D14 决策表与正文、风险表（§24）、延后表（§25）、路线图（§23）四处交叉核对未发现实质矛盾；§10.4 的边角色引用 §12.4.1 词表、§13 样例与 §12.5 契约字段对齐、§18.3 不变量与各章决策对应。发现四处边界模糊，建议在 1.7 中澄清：

1. **§10.4 边角色示例只列 5 种**（subject/object/participant/location/value），而 §12.4.1 词表有 9 种。`origin`/`destination`/`instrument` 是否产生图边应写明。建议规则化为"参数值为实体型即产生对应角色的边"。
2. **§4.6 末尾的引注**（">应充分发挥大模型的能力……让大模型来做复核和修正"）是未整合的批注，与 §12.2/§12.6 的保守立场（"不默认让第二个模型重做全部抽取""定向复核"）需要统一。方向可采纳，但应改写为正文决策：模型复核的触发条件、覆盖范围与成本上限。
3. **实体作用域**表述分散于 §5.3/§9.3/§18.1，未合成一条规则（见 P2-14 第二条建议）。
4. **PPR 启用层级**：§14.5 "可由用户检索选项启用"与 §23-C "评测达标才允许进入自动策略选择"、§25 "默认启用需评测收益"之间，应明确两层开关——用户手动启用可先行放开，自动路由须过评测门。现有文字易被读成矛盾。

## 六、分阶段路线评估

A→F 的顺序、"每项增强必须先有失败样本、基线指标和预期收益"（§23-F）、拒绝预设无依据阈值（§22.6），这些都是高质量的做法。问题集中在**门禁缺位**：

| 阶段 | 现状 | 建议 |
|---|---|---|
| A：EDU 可行性 | 有定性通过条件 | 扩充为"双假设验证"：并入实体链接最小实验（P0-3）；交付物加成本曲线与全书预算表（P1-4） |
| B：最短闭环 | 无退出标准 | 增加退出标准：EDU 通道 vs 分块 RAG 基线的对照实验（P0-1）+ 采用漏斗策略上线并统计人工修正率（P0-2） |
| C：实体关联图 | 有消融设计，无质量门 | 增加实体链接正确率阈值区间；消融实验扩展覆盖"图通道整体关闭"的基线 |
| D：有据问答 | 无退出标准 | 问答金标准应在 C 期间并行构建，避免 D 成为无金标准的纯集成阶段；退出标准至少含引用实际支持率与无依据确定性表达率 |
| E：写作 | 交付清单完整 | 建议补导出格式（docx/Markdown） |
| F：按指标增强 | 设计良好 | 无改动 |

另一个战略层面的观察：方案同时面向古籍/历史研究（玄武门样例、纪年继承、传主补全是其最强场景）与现代文档（RULE 型 EDU、法规示例）。**建议 v1 明确以历史/古籍为旗舰领域**——EDU 上下文补全在该领域价值最高、竞品最少、且团队显然有领域积累；现代文档仅作为通用性验证样例，不必在金标准上平均用力。

## 八、最终结论

这是一份**设计纪律罕见地好**的规划：领域边界克制、幻觉防线完整、图检索可证伪、工程选型经过了真实推敲、评测体系达到研究级。它最大的优点是把"不做什么"写得和"做什么"一样清楚。

它最大的风险不在设计，而在三件事：**核心价值假设（EDU 检索优于朴素 RAG）没有被路线图强制证伪；实体链接这一第二核心假设验证太晚且无质量门；"候选→采用"之间的运营漏斗完全空白。** 三者都属于"补几页文档 + 调整阶段门禁"可解决的缺口，不动摇整体架构。

**建议：按第七节清单补齐三个 P0 项后冻结 1.7 基线；阶段 A 可立即启动**——因为 P0-1（对照实验设计）和 P0-3（链接实验并入）本身就会改变阶段 A 的交付物，先补后跑成本更低。技术栈方面只需补两项决策：中文全文检索方案与回答流式输出边界。

一句话总评：**架构上这是一份"想清楚了再动手"的文档；下一步要做的，是让它的两个核心假设在写第一行代码之前，就站到被证伪的位置上。**
