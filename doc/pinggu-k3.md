> 评估对象：`doc/blueprint.md` v1.6 设计基线（2026-09-02）
>
> 评估日期：2026-09-03
>
> 评估视角：产品定位、领域建模、LLM 工程现实性、检索与架构、实施可行性
>
> 评估文件：`pinggu-k3.md`

---

## 1. 总体结论

**这是一份成熟度明显高于同类平均水平的 AI 平台设计基线，可以进入阶段 A 验证；但核心商业/技术假设（EDU 可被模型稳定、低成本地生成）尚未被任何证据支撑，方案的成功与否几乎完全押注在这一个假设上。**

方案最突出的特质是**克制**：第 2.2 节（非目标）、第 5.2 节（被取消的对象）、第 25 章（延后能力及引入条件）三处呼应，每一项砍掉的东西都写明了"什么条件下才允许加回来"。在 LLM 应用普遍倾向于堆叠智能体、图数据库、多层本体的当下，这种"先做减法并写明复活条件"的设计纪律是稀缺品。

同时，方案对 LLM 工程现实的理解是真踩过坑的：模型不生成 ID、不做字符定位、不写永久哈希（§8.5），定位与校验由系统确定性完成（§12.6），上下文包带指纹留档（§12.3），PPR 只做实验策略且与固定跳共用接口接受消融（D11、§14.5）。这些都不是纸上谈兵能写出来的决策。

主要扣分项集中在三处**尚未展开的设计空白**（实施后一定会撞上）和**量化治理的缺位**（成本、容量、验收阈值）。详见第 4、5 章。

## 2. 方案速览

方案核心链路：文献 → 不可变文献版本 → 文本单元 → 经上下文语义补全生成**事件式语义单元（EDU）** → EDU 参数链接实体并投影为**实体关联图** → 原文/EDU/实体/图四通道混合检索 → 生成可逐句回到原文的问答与研究成果。

关键取舍一句话概括（§26）：**保留原文，做好 EDU，再让图为检索服务。** EDU 是唯一的语义权威记录，图是可重建的查询视图，原文是最终复核依据——三者职责不重叠，这是全方案最重要的一条架构不变量。

## 3. 主要优点

### 3.1 领域建模的克制与可追溯

- 九个核心概念（§5.1）每个都标注了"不承担的职责"，从定义上防止概念膨胀。
- §5.2 把证据、锚点、指称、命题、解释、解析、关系、事件框架、发现九个传统知识工程对象逐一说明"由什么承担"，而不是含糊地删除。这直接回答了评审者最常问的"为什么不要 X"。
- D08"图从 EDU 投影、可重建、不形成第二套权威语义"是从根上避免图谱项目最常见的腐化路径（图与文本两套事实互相漂移）。

### 3.2 EDU 的粒度设计平衡且可操作

- 在三元组（过碎）与长分块（低密度）之间的定位论证（§7.1）清晰；五种类型的划分（§7.2）承认"不是所有文献都以事件为主"，避免了强行事件化的教条。
- §7.4 的拆分/不拆分规则各有四条且互相可对照，§13 玄武门样例逐条验证了这些规则——特别是 U4 的处理（十二名参与者共享一个 EDU、图内多条角色边、展示时恢复完整表述），同时解决了检索粒度和阅读体验两个互相矛盾的需求。
- §11.5 对否定、模态、范围词的保留要求（"谋害≠已经杀害"、"等≠完整名单"）是历史文献场景的真实陷阱，方案在正确的位置设了防。

### 3.3 对 LLM 能力边界的清醒认识

这是全方案含金量最高的部分：

- **职责划分（§12.1）**：模型负责理解，系统负责标识、定位、校验、持久化。§8.5 明确"模型不能自行生成永久标识、数据库主键、内容哈希或可信字符偏移"——这是无数 LLM 项目用幻觉 ID 污染数据库之后才会学到的教训。
- **`contextKey` 回显机制（§12.3/§12.5）**：模型只回显输入中已有的键来指认原文出处，系统据此定位。用最小契约换取了可校验性。
- **校验分层（§12.6）**：JSON Schema 管结构，程序管摘录是否真实存在于指定文本单元，忠实性靠人工抽查与定向复核——承认"忠实性无法仅靠 Schema 判断"是诚实的。
- **单次调用优先（§12.2/D10）**：正确认识到自足表述、指代、时间继承依赖同一次上下文理解，机械拆轮次只会增加费用和漂移；同时留了"评测证明必要才拆"的活口。
- **外部知识默认禁用（§8.3）**：把"模型参数知识"与"文献表达"在数据模型层面隔离，并有不变量 7（§18.3）兜底。

### 3.4 技术栈收敛，且每个"不选"都有论证

- PostgreSQL 同时承担事务、全文、向量（pgvector）、模糊匹配（pg_trgm）、图邻接查询、任务队列（§17.2/§17.5），把基础设施种类压到最低，符合 D14。
- 不引入 Quartz 的论证（§17.8）准确区分了"日历调度"与"持久任务"两类问题；不采用 JPA 的论证（§17.2）准确指出 Spring Data JDBC 聚合的删除重建语义不适合不可变明细记录——这两个判断都是对的，且都是被广泛踩错的坑。
- S3 预签名上传一节（§17.6）的安全细节完整：临时区、HEAD 复核、不采信 Multipart ETag、URL 不落日志。§17.7 甚至预研了 MinerU 无法拉取境外 S3 URL 的现实限制。说明作者读过对方文档，而不只是画了架构图。

### 3.5 评测驱动决策

- §22.1 要求金标准同时覆盖"只给当前段落"和"提供正确上下文"两种输入，防止把模型参数记忆误判为上下文理解能力——这是评测设计里的高级手法。
- PPR 的地位（实验策略、同接口、消融对比、不过线就关闭，见 D11/§14.5/§23 阶段 C/§24.7/§25）是全方案"证据驱动"原则贯彻得最彻底的一条线。
- §12.7 明确"不以 JSON 字符数为唯一目标"，§20.3 明确"不因某模型输出更短就认为更好"，指标设计防 Goodhart 定律。

### 3.6 贯穿样例的质量

§13 玄武门样例不是装饰，而是设计验证工具：§13.3"不允许的推断"七条（甲子不自动等同六月四日、天下大悦不当统计结论等）把模型最容易犯的七类错误显性化为禁止项，这些条目可以直接转化为金标准的"禁止推断"字段（§22.1）。样例与质量门（§22.6 第 1 条）闭环。

## 4. 核心风险与设计空白

以下按严重程度排序。前四条是**实施中一定会撞上的具体问题**，建议开工前补齐。

### 4.1 【最高风险】单一押注 EDU 假设，无降级路线

整个平台的价值链是：EDU 质量 → 实体链接 → 图 → 检索增益 → 回答质量。源头只有一个假设：**模型能在预算内稳定生成忠实、完整、粒度正确的 EDU**。

- 阶段 A 正是验证此假设，方向正确。但 §23 只写了"通过条件"，没写**不通过怎么办**。
- 现实中的失败大概率不是全有或全无，而是部分成立：例如忠实率达标但成本超标 3 倍，或现代文档达标而古文纪年继承大面积失败。
- **建议**：预先定义中间降级形态，例如：
  - L1（全量预处理失败、按需可行）：不批量生成 EDU，仅在查询命中原文后按需生成并缓存（§14.3 的机制天然支持此形态）；
  - L2（古文失败、现代文档可行）：按材料类型圈定首期支持范围；
  - L3（EDU 整体不成立）：退化为"固定版本原文 + 全文/向量检索 + 引用定位"的纯 RAG 产品，保留 §6/§17 的文献版本与资产底座——这部分投资在任何结局下都不浪费。

方案目前缺少这层"失败也有价值"的叙事，对项目治理和投资人/干系人沟通都是隐患。

### 4.2 按需 EDU 与批量 EDU 的双轨一致性空白

§14.3 允许"原文命中但无 EDU 时即时分析，校验后可保存"；§19.3 显示按需生成的输入包含**当前问题**。这引出三个方案未回答的问题：

1. 同一文本单元被问题 A 触发生成的 EDU，与后来批量任务生成的 EDU，如何共存/去重/决定采用状态？按需 EDU 是面向问题裁剪的，它进入默认检索池会不会引入"问题偏向"？
2. 两个用户的问题先后命中同一原文范围，会生成两套相似 EDU 吗？幂等键（§19.4）按"输入范围+配置"生成，但按需生成的输入含问题文本，幂等几乎必然失效。
3. 按需路径的延迟预算：查询链路上插入一次模型调用，首查延迟可能增加秒级到十秒级，§16.6 问答页的交互预期没有对应说明。

**建议**：在 §14.3 补一节"按需 EDU 的生命周期"，明确其作用域（建议默认仅当次查询可见，经人工采用或批量任务确认后才升格）、去重键和延迟预算。

### 4.3 宽关系投影的映射机制缺失

§10.4 规定谓词开放（"谋害""任职""出生于"），§10.5 允许投影为 `opposedTo`、`appointedTo` 等宽关系边用于检索扩展。但方案没有回答：

- 开放谓词 → 宽关系的**映射由谁产出**？模型生成 EDU 时顺带输出（增加单次调用负担，与 §12.2 的克制冲突）？系统维护映射表（开放词表下永远不完整）？
- 宽关系词表本身谁定义、如何演进？
- 谓词的中英文规范未统一：§12.5 示例 `"predicate": "谋害"` 用中文原文，§13.2 用 `plotToHarm`/`appointedTo` 代码值。同一份基线里两种约定并存，实施时会扯皮。

此外，谓词开放词表会让 §14.1"按谓词过滤"的检索能力大打折扣（"诛/杀/弑/诛杀"互不相干），目前只能依赖向量通道兜底。**建议**：明确"谓词存原文表述 + 模型在同次调用中输出可选宽关系标签 + 系统维护词表映射"，并把谓词规范写进输出契约。

### 4.4 项目上下文导致 EDU 作用域分裂

§5.3 规定：使用项目人物表/笔记生成的 EDU 属项目作用域，不可跨项目复用。推论是：**同一文献在两个项目中将产生两套 EDU**，带来三重后果：

1. 存储与处理成本近乎翻倍（§24.9 的成本控制目标与此直接冲突）；
2. 用户在项目 A 修正过的 EDU 错误，在项目 B 里原样复现，§4.6 的修正价值被作用域切断；
3. "为什么同一本书要重新花钱分析"将成为必然的客服问题，§16 产品界面没有对应的解释设计。

**建议**：把补全上下文拆成"文献固有层"（标题、邻文、传主、纪年——这些其实都属于文献上下文）与"项目注入层"（人物表、术语表），争取让绝大多数 EDU 落在文献作用域；项目注入层只影响实体**链接**结果（§9.3 本就是调用后由系统完成），而不进入 EDU 文本本身。这样修正与复用都能跨项目生效。

### 4.5 成本模型缺失

§12.3 的上下文预算意味着：每个分析目标的输入词元 ≈ 目标原文的 2~3 倍（邻文+篇章+概览重复携带），再加 EDU 输出。粗略估算，一部 50 万字文献的首轮处理是数百万词元量级的调用。方案有成本指标（§12.7、§20.3）和控制手段（§24.9），但：

- 没有**量化目标**（每条采用 EDU 成本上限、单文献处理成本上限）；
- 没有**成本随文献库增长的曲线**推演（文献库开放导入 + 项目作用域分裂 = 成本与内容量的超线性关系）；
- 按需生成（§14.3）使查询侧成本也不可忽略。

**建议**：阶段 A 的交付物中增加"单文献端到端处理成本实测"，并在 §24.9 补充预算告警的阈值设定方式。

### 4.6 单次调用的输出质量风险

D10/§12.2 选择单次调用是正确的默认，但一次输出"EDU 文本 + 谓词 + 多角色参数 + 时间 + 限定 + 来源摘录"的复合结构，输出越长，中后段字段的质量衰减越明显（已知的结构化输出长尾问题）。§22.5 的分项指标（主体错置、指代错误、时间错误）恰好能观测这个，但**阶段 A 的交付清单（§23）没有把"单次 vs 拆分调用"列为对照实验**——§12.2 自己说了"评测证明必要才拆"，那就应该在阶段 A 把这个对照做掉，而不是默认单次然后等问题出现。

### 4.7 权限 × 向量检索的性能路径未验证

§21.1 的权限交集规则（EDU 可见范围 ≤ 引用版本权限交集）语义正确，但实现上要求向量检索携带复杂的权限过滤。pgvector 在强过滤场景下（过滤后候选稀疏）召回质量会下降，这是已知工程难点。§17.5"实测瓶颈后再拆"的原则没错，但权限过滤不是性能优化项，而是**正确性前置项**（漏过滤是安全事故），建议在阶段 B 就纳入实测，而非等 C/D。

### 4.8 时间保守策略与"人物时间线"交付物的张力

§11.3/§13.3 正确地禁止了伪精确历法转换和"甲子=六月四日"式推断。代价是：历史文献场景下，大量 EDU 的时间状态将停留在"仅原文/可继承但不确定/未知"。而阶段 C 承诺交付"人物时间线"（§23）。一条大半节点时间未知的时间线如何渲染、如何排序、如何向用户解释，§16.4/§16.5 没有兜底设计。跨来源关联（§10.7）依赖的"时间重叠"信号在同一约束下也会大面积失效。**建议**：时间线按"叙事序"（原文出现顺序 + 相对先后关系型 EDU，§10.6）为兜底轴，规范时间为增强轴，并在阶段 C 验收标准中写明这一预期。

### 4.9 模型复核的定位含糊

§4.6 末尾以引用体加入"应充分发挥大模型的能力……让大模型来做复核和修正"，与 §12.6"不默认让第二个模型重做全部抽取"、§24.6"不依赖模型自报置信度"存在张力。模型复核并非不可用，但需明确：复核什么字段（时间继承、外部知识补全是高价值目标）、复核结论的证据地位（建议仅作为批量审核的排序信号，不自动改状态）、如何防止同模型自我强化（复核应换模型或换提示分布）。目前这句话悬在半空，实施时容易被解读为"让模型自己审自己"。

## 7. 结语

这份蓝图最难得的不是它设计了什么，而是它**拒绝设计什么**——并且每一处拒绝都附带了重新开启的条件。这使它在结构上天然抗腐化：未来任何"要不要加 X"的争论，都会被引导回"X 的引入条件满足了吗"。

它的风险分布也同样清晰：工程风险被压得很低，真正的不确定性全部收敛到一个上游假设——**EDU 能否被稳定、忠实、低成本地生成**。这是正确的风险形态（把不确定性放在最早、最便宜的地方验证），但方案目前只规划了验证，没有规划验证失败后的世界。补上降级路线、双轨 EDU 一致性、宽关系机制和成本模型这四块短板之后，本方案可以直接作为实施基线。

**评估结论：通过（有条件）—— 建议完成 P0 级修订后进入阶段 A。**
