## 1. 总评

**有条件通过。设计纪律和工程判断明显高于同类规划，可以启动阶段 A；但阶段 A 必须验证「文献研究场景下的 EDU」，不能把对话记忆论文的分数当成先验。**

这份规划最强的地方，是它把一套外来的记忆表示（事件式 EDU）改写成了学术工具能用的产品约束：原文不可变、补全可检查、图可重建、引用必须回到固定版本。第 2.2、5.2、25 章三处呼应，把常见死亡路径——多层图、本体编辑器、智能体默认路径、为概念对称性建对象——事先封死，并且写明了复活条件。这不是「想得全」，是「删得有理由」。

真正的不确定性不在 Spring 还是 PostgreSQL，而在三句还没被证伪的话：

1. **EMem 的杠杆在文献里仍然成立。** 论文证明的是：在多轮对话记忆上，短小自足的事件命题比三元组和长分块更好检索。溯知把它迁到书籍、论文、档案、尤其是古籍。源域允许轻度推断并用会话时间戳当时间；目标域默认禁止外部知识，时间在文本内部、常常不可精确解析。论文数字不能直接搬家。
2. **EDU 同时当记忆、索引、图节点、引用桥梁、事件记录和修正单元，这六件事能共存在同一个对象上。** 表示一旦粒度错了，六条链路一起坏。这是表示层的单点故障，不是模块拆分能解的。
3. **研究者会以 EDU 为工作面，而不是只把它当检索中间件。** 阶段 A–D 几乎全在建抽取工厂，写作和阅读工作流是后置的。对「研究与写作平台」来说，这是产品假设顺序反了。

工程底座可以开工。产品与表示假设必须在写第一张业务表之前被摆到能失败的位置上。

## 2. 方案在解什么问题

核心链路可以压成一句：

**固定版本的文献 → 上下文补全后的事件式 EDU → 实体关联图（可重建）→ 原文/EDU/实体混合检索 → 能点回原文的回答与写作。**

第 26 章的取舍也准确：**保留原文，做好 EDU，再让图为检索服务。**

这套取舍对学术工具是对的。普通 RAG 的病是分块太大、引用漂；知识图谱的病是三元组把一次事件拆散，生成时还得拼回来；摘要的病是细节被覆盖。EDU 想站在中间：短到能检索，完整到能读，结构化到能投影成图，同时不取代原文。

如果只评「有没有把知识工程的常见坑堵上」，这份文档接近优秀。问题是：它默认 EDU 这个中间物在文献场景里也会成为杠杆。这需要证明，不能从论文标题推理出来。

## 3. 突出优点

### 3.1 学术工具的信任链是完整的

D02 / D03 / D12 加上第 18.3 节九条不变量，把「OCR 重做不能静默改研究依据」「外部知识不能伪装成上下文补全」「删除原文不能留下看起来有效的公开引用」写成了系统性质。多数知识应用把引用当成生成后的装饰；这里把引用当成数据约束。这一条单独就比很多「AI 研究助手」规划更接近真能用的学术产品。

### 3.2 对 LLM 会撒谎的位置，切得很准

模型负责理解，系统负责标识、定位、校验、链接、持久化（§12.1）。模型只回显输入里已有的 `contextKey`，不能自己发明主键、哈希或字符偏移（§8.5 / §12.5）。这不是风格偏好。对话系统和抽取管线里，幻觉 ID、自报依据、局部 ID 交叉引用，是污染数据库的常规事故。把这些从输出契约里拿掉，比再加一个「反思智能体」有用。

分层上下文包（§12.3）同样老练：分析目标不能被摘要替代，预算先保原文再加背景，标签区分 `primary-source` 和 `context-only`。补全三分法（Explicit / Contextual / External，§8.3）加上金标准必须同时测「只给当前段」和「给正确上下文」（§22.1），构成对「模型记忆冒充文献」的闭环。

### 3.3 图被降级成可证伪实验，这是对论文的正确阅读

蓝图没有把 EMem-G 整套搬过来。它砍掉独立 Argument 节点、砍掉默认 PPR、砍掉两阶段模型调用，只保留「先 EDU、再要素与角色、再投影为图」的表示思想（§10.2）。这是对的。

论文自己的结果也支持这种克制。LoCoMo 上，EMem（只要 EDU 向量 + 偏召回筛选）与 EMem-G（再加图和 PPR）的总体 LLM 分数同为 **0.780**（gpt-4o-mini）。图对多跳略有帮助，对整体不是决定性的。后续复述也指出：杠杆在事件式表示，不在图传播。蓝图把固定跳当默认、局部 PPR 当实验、专用图库当延后能力，和这条证据一致。

### 3.4 领域模型的减法是可执行的

九个核心概念每个都写了「不承担什么」（§5.1）。证据、锚点、指称、命题、解释、解析、项目关系、事件框架、发现九个对象被降级，并给出提升条件（独立查询、权限、版本或评审需求）。这比空喊「保持简单」更可操作：以后争论「要不要加 X」，会被引导回「X 是否已经产生独立生命周期」。

玄武门样例（§13）也不是装饰。U4 十二名参与者共享一个 EDU、图上多条角色边、展示时恢复完整表述，同时服务了检索粒度和阅读。§13.3 的禁止推断清单可以直接变成金标准的负例。

### 3.5 工程选型经过真实推敲

单应用、PostgreSQL 一统、S3 预签名直传后 HEAD 复核、解析器接口隔离 MinerU、任务表 + `FOR UPDATE SKIP LOCKED`、不用 JPA（聚合删除重建不适合不可变明细）、不用 Quartz（日历调度 ≠ 持久任务），这些判断都站得住。Spring Boot 4.x + Spring AI 2.0 在 2026-09 已是受支持组合；实施时固定一对 BOM（建议 Boot 4.1.x + Spring AI 2.0.x），不要口头兼容 4.0 却被 starter 元数据拉到 4.1。

## 4. 核心判断：这是一次领域迁移，不是一次复现

蓝图写得很清楚：采用论文的表示思想和双入口检索思想，不照搬节点和调用方式（§10.2）。但正文仍容易让读者觉得「论文已经证明 EDU 可行，剩下是工程」。下面四条差异决定了阶段 A 必须重新做实验。

### 4.1 源域是对话记忆，目标域是文献研究

EMem 的任务是：多会话对话里，问答模型如何回忆「我的宠物」「那次会议」。文献平台的任务是：在不可变版本的书籍、论文、档案里，研究者如何核对「文献说了什么」，并写回带引用的文字。

对话记忆允许、甚至需要轻度推断——论文明确说 EDU 有时包含 lightly inferred information，时间可从会话时间戳推导。溯知默认禁止外部知识，时间必须来自原文或给定上下文（§8.3、§11、§13.3）。**更严的忠实性约束会降低召回、提高拒绝率，论文的 0.78 不能当天花板，更不能当地板。**

建议在 §23 阶段 A 写死一句：对照实验使用本平台的补全规则和禁止推断清单，不引用 LoCoMo / LongMemEval 作为通过条件。那两个数据集最多当管线打通的玩具。

### 4.2 时间在对话里是元数据，在文献里是研究对象

EMem 的时间几乎是会话日期。历史文献的时间是纪年、干支、相对词（「是岁」「明年」「是月」）、互见和追叙。蓝图的时间模型（§11）在工程上保守且正确：不造伪精确公历、继承必须进补全说明、「甲子」不等于「六月四日」。

代价是：大量 EDU 的时间会停在「仅原文 / 不确定 / 未知」。阶段 C 却交付「人物时间线」（§23）。一条大半节点时间未知的时间线，按公历轴渲染会空洞，按叙事序渲染才诚实。跨来源关联依赖的「时间重叠」（§10.7）在同一约束下也会大面积失效。

**建议：** 时间线的主轴定为「文献叙事序 + 关系型 EDU 表达的先后」，规范时间只是增强轴。阶段 C 验收必须包含「时间大量未知时仍然可浏览」，否则时间线是虚假承诺。

### 4.3 图在论文里是检索插件，在产品里会被当成传记

论文里图的理由是联想召回。蓝图里图有两个未分开的理由：

| 理由 | 需要的质量 | 失败后果 |
|---|---|---|
| 检索增益（固定跳 / PPR） | 链接正确率、边噪声、延迟 | 关掉图通道，问答仍可用原文+EDU |
| 浏览与组织（实体页、事件页、时间线） | 同一质量，但用户会把页面读成「这个人做了这些事」 | 错误链接会以传记形态呈现，损害信任 |

D05、§8.6 正确地规定：EDU 不是客观事实，矛盾可以并存。但 §16.4 的实体页是「按时间排序的相关 EDU + 相关实体」。用户不会先读设计文档再看页面。产品会在界面上表现成事实引擎，即使领域模型拒绝当事实引擎。

这不是要加裁决系统（第 2.2 节不建设事实引擎是对的）。这是要在实体页、事件页、回答页把「来源陈述」做成默认视觉语言：每条 EDU 必须带着文献题名、版本、必要限定（否定、据称、计划）出现，矛盾并陈是主交互，不是高级选项。

**建议：** 把「图作为浏览面」和「图作为检索策略」拆开验收。检索侧沿用现有消融。浏览侧单独验收：矛盾 EDU 是否可见、限定是否丢失、用户会不会把投影边（`opposedTo`）读成原文。

### 4.4 论文用两次模型调用，蓝图用一次；两边的风险不同

EMem 是 `g_EDU` 再 `g_ARG`。蓝图默认一次调用同时出 EDU、要素和角色（D10），理由是同一次上下文理解、少漂移、省费用。作为默认值合理。

但一次输出「自足文本 + 谓词 + 多角色 + 时间 + 限定 + 摘录」的复合 JSON，长尾字段质量会掉。U4 这种参与者名单会把对象撑得很大。§12.2 说「评测证明必要才拆」，阶段 A 交付物却没有把「单次 vs 拆分」列为对照。这是自己的原则没有写进自己的实验。

**建议：** 阶段 A 必做三次对照：单次调用、先 EDU 再要素、以及「只要 EDU 文本、不要图」。第三项直接对应论文结论——如果只要 EDU 文本就已经明显优于分块，阶段 C 的图可以从「检索必须」降为「浏览增值」。

## 5. 表示过载：一个对象干了六件事

EDU 在规划里同时是：

1. 核心语义记忆（D04）
2. 检索单元（§14.1）
3. 图节点（§10.3）
4. 回答到原文的桥梁（D12）
5. 来源特定的事件记录（D09）
6. 纠正和替代的单位（D13）

六件事能叠在一起，前提是粒度规则（§7.4）在真实语料上稳定。我不认为这条已经成立。

### 5.1 「一项可独立回答的问题」是循环定义

§7.4 说一个 EDU 应围绕一项可独立回答的问题。独立相对于谁、相对于哪类问题，没有操作定义。对「李世民何时被加中书令」是一项；对「玄武门有哪些人」是另一项；对「谋害与诛杀的关系」又是一项。标注者会为边界吵架，模型会在不同运行里给出不同切分。§12.7 有「错误拆分率」，但金标准本身的标注者一致性（IAA）没有进入评测体系。

**没有 IAA 的金标准，不能支撑 §22 那套精细指标。** EDU 边界是判断题，不是 NER 那种相对硬的跨度。阶段 A 应先报拆分/合并的标注者一致率。如果两人在玄武门材料上的 EDU 切分一致率低于可接受区间，说明粒度规则还不能当验收标准，只能当提示词启发式。

### 5.2 文言文的信息密度会把阅读器挤爆

§13 用的是相对清爽的《旧唐书》叙述。真正的编年体、纪传体常见情况是：一句之内叠时间、身份、行动、结果、史官评价。按 §7.4 严格拆——身份与后续行动分开、评价与事件分开、条件单独成条——短原文右侧会出现一排 EDU。

§16.3 的三栏布局没有处理「原文短、EDU 多」。用户会觉得系统在把一句话改写成五条卡片。这会直接伤害「比长分块更聚焦」的价值主张：聚焦的是机器，不是人。

**建议：** 阅读器按原文句或文本单元聚合 EDU，默认折叠结构化字段，只在选中时展开。阶段 B 的可用性标准应包括「一屏内能对照原文看完当前范围的 EDU」，而不是「EDU 条数等于抽取条数」。

### 5.3 引用链比「回答 → 原文」多一跳

NotebookLM 一类产品的引用是答句到段落。溯知是答句 → EDU → 原文。多出来的一跳在学术上有价值：可以看到「之」被补成谁、年号从哪来。若界面先展示 EDU 再让用户找原文，复核会变慢，价值主张第 5 条（比直接问答更可复核）会反转。

§15.2 的点击展开清单是对的，顺序应是：**先原文摘录，再 EDU 自足表述和补全说明。** EDU 是解释层，不是复核终点。D12 在数据上已经这样规定，交互上要写死，避免实施时做成「引用徽章 → EDU 卡片 → 再点一次才见原文」。

## 6. 产品顺序：工厂建得很完整，工作室还是草图

一句话定义是「研究与写作平台」（§1.1）。实施路线的重心是抽取、链接、检索。写作在阶段 E，阅读工作台在阶段 B 才出现，而且 B 的交付是批量 EDU，不是「边读边分析」。

### 6.1 缺第一用户

规划同时覆盖书籍、论文、报刊、档案、网页、法规。样例和补全规则的旗舰域明显是历史文献。现代文档的 RULE/EVALUATION 类型更像是防止被说成「只做史书」。

两线并行会稀释阶段 A。EDU 的补全价值在省略主语、庙号、纪年继承上最高；在现代论文里，分块 RAG 往往已经够用。若金标准在「古文 / 现代」上平均用力，古文特有的硬问题会被平均数掩盖。

**建议：** v1 写明旗舰用户——以固定版本文献做核对、比较和写作的历史研究者（含读史、校注、传记、制度史）。现代文档只作迁移探针，不参与阶段 A 的通过判定。竞品对照至少点名：普通 PDF QA / NotebookLM 类、三元组知识图谱、纯阅读站（如读通鉴这类原文工作台）。溯知的差异应是「补全可检查的语义记忆 + 矛盾并陈 + 点回固定版本」，不是「又一个带聊天框的文库」。

### 6.2 批量抽取不该是默认工作方式

阶段 B 的闭环是：导入 → 不可变版本 → 批量 EDU → 检索。对一部中型史书，这意味着用户上传之后要等一次昂贵的全量处理，才能开始研究。§4.3 允许用户主动对范围发起分析，§14.3 有按需生成，但它们被写成回退，不是主路径。

研究者的真实节奏更接近：打开一卷，标范围，先看原文，对当前屏生成 EDU，问一个问题，再决定要不要处理下一章。按需先行、批量后置，和 §24.9 的成本控制、§2.3「未生成 EDU ≠ 没有信息」是同一方向。

**建议：** 阶段 B 的最短闭环改成「阅读器可用 + 当前范围生成 EDU + 原文始终可检索」。全文献批量作为可选加速，不作为第一次可用的前提。按需 EDU 的生命周期（作用域、是否带问题偏置、如何与批量去重）必须在开工前写清——这一点与 k3 评估一致，此处不重复展开，只强调它应上升为主 UX，而不是检索补丁。

### 6.3 写作产品几乎没有理论

阶段 E 列出备忘、提纲、文章、句级引用、支持性检查。没有回答：文章从哪来（选 EDU 拼、从问答升格、还是空白写再挂引用）？与外部工具（Word、Zotero、Markdown）如何交接？导出是什么格式？

对写作平台，导出不是阶段 F 的增强项。不能把成果带出系统，研究工作台就还是演示。阶段 E 至少要有 Markdown 导出和引用清单；docx 可稍后。

### 6.4 修正价值会被作用域切断

§5.3：用了项目人物表的 EDU 属于项目，不能当文献级复用。同一文献进两个项目，就可能付两次抽取费、改两次同样的错。D01「文献是独立资源」的经济逻辑在这里被项目上下文打穿。

更干净的切法是：EDU 文本只使用文献固有上下文（标题、邻文、传主、纪年）；项目人物表只参与调用后的实体链接。这样修正和复用留在文献层，项目差异留在图层。k3 已指出这条，我同意，并把它看成 D01 能否成立的条件，而不只是成本优化。

### 6.5 缺一场便宜的产品实验

阶段 A 全是模型对照。可以在几乎不写平台代码的情况下先测产品假设：选一篇传记，人工按 §7/§13 写 EDU，给一位真实用史书的人，看他是否用这些卡片做问答、核对和提纲。如果人手 EDU 都没人用，提高抽取分数没有意义。

这不是要延后阶段 A。这是让阶段 A 同时产出两类证据：抽取可行性，以及「EDU 作为工作面」的可行性。后者失败时，EDU 降级为检索中间件，阅读器仍以原文为中心——这仍然是一个产品，而且更接近读通鉴已经验证过的工作方式。

## 7. 旗舰域的工程缺口：中文、古籍、定位

仓库里已经有一份对读通鉴的字体、简繁、异体和索引对齐分析。蓝图作为「从零设计」可以不继承旧对象，但不该假装中文文献的文本层问题不存在。

### 7.1 中文全文检索不是默认就能用的 PostgreSQL

§17.2 写「主数据库承担全文检索」。PostgreSQL 默认分词对无空格中文基本无效；`pg_trgm` 只适合短名称模糊匹配。没有 zhparser / pg_jieba / pg_bigm（或明确的 trigram 兜底）之前，§14 的「原文全文召回」在中文上不成立。glm 评估已列这项，结论正确，必须写入技术栈表。

对古籍还要加一层：**检索用规范文本，展示用底本。** 繁简、异体、旧字形若只在界面转换、不在索引层归一，「建成」「建成」和「李建成」的召回会按用户当前用字分裂。读通鉴的经验是：底本繁体、简体是阅读面、异体用词典而不是一刀切、人名生僻字要保护、简繁转换会改字符串长度从而打错锚点。

蓝图的来源引用依赖摘录定位（§8.5、§12.6）。**简繁转换导致的偏移，和 OCR 错字导致的摘录对不上，是同一类定位事故。** 只把 quote 校验改成模糊匹配不够，还要规定：权威偏移永远落在不可变版本的底本文本上；其他阅读面通过映射表换算。

### 7.2 实体链接在古籍里不是后处理，是产品本身

§9.3 把链接放在模型调用之后，阶段 C 才建设实体页。对历史文献，用户真正会搜的是「太宗」「秦王」「天策上将」「二郎」。链接错了，实体页就是错的传记，图扩展就是错的连坐。

同名消歧、官职性称谓、庙号谥号、传主省略，是领域级难题，不是五步管线写在纸上就会收敛。阶段 A 的金标准应同时标注：规范名、原文写法、是否允许链接、不可链时的正确形态。冷启动也要写：项目人物表 + 传主 + 高频未链接候选，而不是指望第一篇文档自动长出一张能用的实体表。

glm 把链接质量门排成 P0，我同意，并补一条产品判断：**宁可不链，也不要错链。** 未链接的事件要素仍走文本和向量（§10.2 已有）。错误合并的伤害远大于图暂时不连通。§24.5 写了合并污染，默认策略应把这个不对称性写进链接阈值。

### 7.3 OCR 与解析质量是一切下游的上游

「OCR 和解析质量」出现在文献库界面（§16.2），没有进入 §22。扫描件的阅读顺序、栏切分、页码漂移，会让再好的 EDU 契约也定位失败。MinerU 只有 Web API 一个初版实现（§17.7），敏感文献的本地/私有化路径只有接口，没有可行性结论。§21.2 的模型数据边界同样适用于解析提供方。

阶段 B 应有解析质量门：文本层覆盖率、抽检阅读顺序、定位成功率按「文本 PDF / OCR PDF / 纯文本」分桶。不能只用玄武门这种已清洗文本当质量门。

## 8. 实施与架构上还要补的洞

以下与 glm / k3 重叠的，只保留判断和我建议的写法。

### 8.1 阶段 A 没有失败后的世界

价值链是 EDU 质量 → 链接 → 图 → 检索增益 → 回答。源头假设失败时，§23 没有降级形态。现实很少全有或全无，更常见的是：现代文档还行、古文纪年大面积失败；忠实率够、成本超三倍；EDU 文本有用、结构化角色不稳定。

建议预定义：

| 级别 | 含义 | 仍可交付 |
|---|---|---|
| L1 | 批量不划算，按需可行 | 阅读器 + 当前范围 EDU + 原文检索 |
| L2 | 只有部分材料类型可行 | 收窄旗舰域，不装成通用文献平台 |
| L3 | EDU 整体不成立 | 固定版本原文 + 全文/向量 + 引用定位；文献底座不浪费 |
| L4 | EDU 文本成立，图/链接不成立 | 关掉实体页默认视图，问答只用原文+EDU 通道 |

L3 特别重要：第 6 章的文献版本、文本单元、权限和 S3 资产，在任何结局下都值。阶段 A 的叙事应是「验证 EDU 是否值得成为核心记忆」，不是「验证我们是否能做成 EMem 的产品版」。

### 8.2 候选到采用是运营空洞

状态机有 Proposed / Active（§7.7），没有默认采用策略。等人工，一部书的 EDU 量不可审；全自动采用，又和全文的审核立场打架。§16.7 的高影响队列是正确方向，但没有漏斗就只是清单。§4.6 末尾「让大模型来做复核」仍是批注，和 §12.6「不默认第二模型重做全部抽取」冲突。

建议写成正文：低风险自动采用并标可信级；高影响进队列；模型复核只做排序信号，换模型或换提示，不自动改状态；项目可开全人工开关。审核吞吐写入 §24。

### 8.3 谓词开放、宽关系投影、样例角色，三处还没对齐

- §12.5 谓词用「谋害」，§13.2 用 `plotToHarm` / `appointedTo`。
- §13.2 U4 的「领导者」不在 §12.4.1 固定角色词表里。
- §10.4 边示例只有 5 种角色，词表有 9 种。
- 开放谓词会打散按谓词过滤；宽关系由谁从「谋害」映射到 `opposedTo`，没有机制。

这些是实施时会扯皮的契约问题，不是风格问题。输出契约应规定：谓词保存原文或规范中文；宽关系是可选标签，词表由系统维护；样例角色必须落在固定词表，特殊含义走 `roleName`。

### 8.4 技术栈其余备注

- 回答生成与任务进度不是同一件事。任务进度轮询成立；问答和长文应流式输出。不要用 §17.8 的「首期不使用 SSE」盖住生成 UX。
- 多通道融合 v1 用 RRF 即可，写明，避免临时加权。
- 权限过滤对 pgvector 是正确性前置，不是性能优化。漏过滤是安全事故，阶段 B 就要测。
- 前端选 React + shadcn，而仓库已有的领域分析对象是 Vue 3 阅读站。可以选 React，但要承认这是团队栈决策，不是文献阅读的最优默认；阅读器的长文排版、简繁、字体、锚点，复杂度会接近一个独立产品。
- 容量要有量级假设（例如单项目十万 EDU 内、全库千万内），否则 D14「先单库」无法被证伪。

## 9. 内部一致性

D01–D14、第 23 / 24 / 25 章整体自洽，没有发现会推翻架构的硬矛盾。需要 1.7 澄清的边界：

1. §4.6 批注与 §12.6 保守复核立场。
2. 实体作用域分散在 §5.3 / §9.3 / §18.1，未合成一条规则。
3. PPR「用户可开」与「评测后才自动路由」应分成两层开关。
4. 样例角色、边角色示例、固定词表三者未对齐。
5. 文档自称从零、不继承旧对象（§0.1），但旗舰域的文本层问题（简繁、异体、锚点）已被同源材料证明存在。从零指领域对象，不指忽略中文文献的物理现实。

## 10. 修改建议（按开工优先级）

**P0，写进 1.7 再开阶段 A：**

1. **领域迁移实验。** 阶段 A 使用本平台补全规则，不把 LoCoMo 分数当通过条件。必做对照：分块 RAG、只要 EDU 文本、单次调用、拆分调用。通过标准表述为「在旗舰文献上，EDU 文本通道不劣于分块基线，并提供基线没有的可检查补全」——图不是 A 的通过条件。
2. **失败降级。** 写入 L1–L4。任何阶段 A 结果都要落到一个可交付形态。
3. **旗舰用户。** 写明历史文献研究者为 v1 第一人格；现代文档不作 A 的通过判定。
4. **采用漏斗 + 复核边界。** 低风险自动采用；高影响进队列；模型复核只排序、不改状态。删掉 §4.6 悬空批注，改成正文。
5. **按需为主路径。** 阶段 B 最短闭环改为阅读器 + 当前范围 EDU；按需生命周期（不带问题进补全、文献级可复用、与批量去重）写清。

**P1，阶段 A/B 内关闭：**

6. 金标准报 EDU 边界 IAA；链接与指代作为 A 的附属标注，不等到 C。
7. EDU 文本只用文献固有上下文；项目人物表只影响链接。
8. 技术栈补中文全文方案 + 检索归一层（NFKC、简繁/异体、底本偏移为权威）。
9. quote 校验区分 OCR/异体差异与模型改写；模糊匹配放行前者。
10. 谓词/宽关系/角色词表与样例对齐；U4「领导者」改为词表角色。
11. 时间线以叙事序兜底；实体页默认「来源陈述 + 矛盾并陈」。
12. 阅读器聚合 EDU，引用点击先展示原文。
13. 成本与容量给出量级：每千字费用、单文献预算、单项目 EDU 上限。
14. 解析质量分桶指标；MinerU 自部署或本地解析的可行性一句结论。

**P2，阶段 C 前：**

15. 图检索与图浏览分开验收；链接默认宁缺毋错。
16. 回答流式、任务轮询分开写。
17. 融合方法定为 RRF；权限过滤向量检索纳入 B。
18. 研究成果 Markdown 导出；被引用 EDU 被替代时，引用方标复核。
19. 前端栈作为团队决策明示；阅读器按长文产品而不是普通 CRUD 页来估工。

## 11. 结论

溯知 v1.6 是一份**把外来记忆论文改写成学术产品约束**的设计，不是一份堆智能体的愿景书。原文权威、EDU 可检查、图可重建、延后能力带复活条件——这四件事做对了，后面的系统才有资格叫研究工具。

它还不是一份可以直接施工到「研究与写作平台」的产品规格。缺的不是模块图，而是：

- 承认 EMem 证明的是对话记忆，不是古籍文献；
- 承认 EDU 现在是六职合一的表示赌注，粒度必须先被标注者复现，再被模型复现；
- 承认用户先要一个能读、能核、能渐进分析的工作室，而不是一座等全量抽取结束才开门的工厂。

**评估结论：有条件通过。** 按第 10 节补齐 P0 后冻结 1.7，立即开阶段 A。阶段 A 的成功标准不是「我们实现了论文」，而是「在自己的旗舰文献上，自足 EDU 是否值得成为核心记忆；如果值，值在阅读、检索，还是两者都有。」

一句话：**架构已经足够克制，可以把不确定性留给最早的实验；不要把论文里的记忆单元，未经迁移证明，就写成产品里的第一公民。**
